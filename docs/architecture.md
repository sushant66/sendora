# Architecture

Sendora is a single Next.js (App Router) application — no separate backend. Route handlers
and server components are the API surface; business logic lives in framework-free `lib/`
modules that are independently unit-testable.

## Layers

```
app/
  (auth)/sign-in            Google sign-in (unauthenticated shell)
  (app)/                    Authenticated shell (AppShell + SideNav)
    contacts/               US1 — import + manage recruiter contacts
    templates/              US3 — starter library + custom template CRUD
    compose/                US2 + US4 — single and bulk send
    history/                US5 — sending history
    settings/email-account/ FR-019a — connect Gmail
  api/                      Route handlers (thin: auth → Zod → service → response)

lib/
  db/          Drizzle schema + client (typed data layer over NeonDB)
  auth/        Auth.js config + session helpers (per-user scoping, FR-022)
  validation/  Zod schemas — the single source of truth at each trust boundary
  import/      CSV/xlsx/paste parsers → one shared normalize→validate→dedup pipeline
  contacts/    Contact persistence + search
  templates/   Merge-field vocabulary/renderer, sanitize-on-save, preview, CRUD
  sanitize/    Server-side rich-text HTML sanitizer (strict allow-list)
  email/       EmailProvider seam + Gmail impl + MIME + connected-account service
  send/        Send service (dedup → per-recipient send → snapshot outcomes)
  history/     History listing + re-contact lookup
  crypto/      Refresh-token encryption at rest (AES-256-GCM)
  http/        Response helpers + the route() error-to-HTTP mapper
  errors.ts    Domain errors thrown by services

components/    Astryx-based UI (client components behind server pages)
tests/         unit · contract (route handlers, mocked services) · integration · e2e
```

## Key decisions

- **Trust boundaries validated with Zod** (Constitution I). Uploaded/pasted rows, all API
  bodies, OAuth data, and env vars are parsed to validated types that flow through `lib/`.
- **Provider-agnostic sending** (`lib/email/provider.ts`, FR-019c). The Gmail provider is
  the only implementation; the send flow, batching, and per-recipient results are provider-
  independent. A fake provider (`fake-provider.ts`) makes the whole send flow testable
  without network access.
- **One import pipeline** for all three input methods, so validation/dedup/reporting live
  in one tested place (`lib/import/pipeline.ts`). Pure and DB-free.
- **Merge rendering is total** — never emits a literal `{{token}}` (`lib/templates/merge.ts`,
  SC-004); a closed vocabulary is validated at template save time (FR-011).
- **Send is snapshot-based** — each `SendRecord` stores the rendered, sanitized content at
  send time, so editing a template later never alters history. Partial failures never roll
  back successful sends (FR-018).
- **Per-user isolation (FR-022)** — every contact/template/batch/record query is scoped to
  the authenticated user; starter templates are the only cross-user-readable, read-only rows.

## Data model

See `specs/001-recruiter-outreach/data-model.md`. Entities: `User`,
`ConnectedEmailAccount`, `RecruiterContact`, `EmailTemplate`, `SendBatch`, `SendRecord`.
Migrations are generated by drizzle-kit into `drizzle/`.

## Request lifecycle (send)

1. `POST /api/send` → `requireUser()` → `SendRequestSchema.parse(body)`.
2. `sendEmails()` loads the active connected account (else `409 no_active_account`),
   resolves the provider, dedups recipients (FR-016), and resolves the base content.
3. A `SendBatch` is created; `runSendLoop()` renders per recipient and sends one message
   each via the provider seam, recording each `SendRecord` outcome. A reauth failure marks
   the account `expired` and fails the rest (FR-019b).
4. The batch is completed and an aggregate + per-recipient summary is returned.
